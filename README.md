# optio-agent-kit

Guides that let coding agents — including small, fast models — work in the
[Optio](https://github.com/jonwiggins/optio) codebase without getting lost, plus an air-gapped layer for
teams that run Optio with no internet. Everything here works offline: bash, git and coreutils only.

Checked against upstream Optio `d72f1cd1` (2026-11-01) — see `OPTIO_BASE`.

## The problem it solves

Optio's root `CLAUDE.md` imports a 67 KB `AGENTS.md` (~30k tokens) into every session, and the repo has
~2,900 files across seven apps and packages. A capable model copes; a small one spends its turns reading the
wrong things. The built-in Explore/Plan subagents of Claude Code don't read `CLAUDE.md` at all.

## What it adds to an Optio checkout

**Layer `core` — generic, upstream-able** (`core/`)

- `docs/agent-guides/README.md` — Optio's main ideas on one page (work model, pods and the run protocol,
  the life of a task, the control plane, integrations, ownership) and an index of the area guides.
- An `AGENTS.md` in each main folder — what the area is, its **main ideas**, a file map, how to change it
  safely — and a `CLAUDE.md` next to it that imports it (the upstream convention, so every agent reads the
  same text). Folders: `apps/api`, `apps/api/src/services`, `apps/web`, `apps/cli`, `packages/*`, `helm`,
  `images`, `scripts`.
- A "Start here" section in the root `AGENTS.md`, between markers.
- `helm/VALUES-MAP.md`, generated by `scripts/helm-value-map.sh` on every install: each Helm value → the
  template that uses it → the env var it becomes → the source files that read it; the env vars the API reads
  that the chart never sets; and `values.yaml` keys no template reads. Made from the checkout's own chart and
  code, so it matches your fork. No helm needed.
- `scripts/check-agent-guides.sh` — fails when a guide names a file that no longer exists or the value map
  is out of date.

**Layer `airgap` — our fork** (`airgap/`)

- Root `CLAUDE.md` router (~100 lines, replaces the `@AGENTS.md` import): rules, map, symptom → file routing.
- `docs/airgap/` — what the fork is and how we work (`README.md`), known gaps and fixes (`gotchas.md`),
  and two **team-owned** files the kit never overwrites: `site-facts.md` (registry, release, hosts) and
  `worklog.md` (what we are doing now, decisions, log — the agents' memory between sessions).
- Air-gap notes appended to the `CLAUDE.md` of `apps/api`, `helm`, `images`, `packages/ticket-providers`, `scripts`.
- `.claude/`: settings that block noisy folders and web tools, a model-alias example for LiteLLM, the
  `optio-scout` read-only subagent, and skills: `optio-debug-gitlab`, `optio-debug-jira`,
  `optio-rebuild-publish`, `optio-debug-live`, `optio-sync-upstream`, `optio-refresh-guides`.
- `scripts/airgap/impact.sh` — changed files → which images to rebuild, Helm keys, tests.
- `MANIFEST.md` — what belongs where, change → rebuild matrix.

**Deploy starter — chart and images only** (`deploy/`, not installed into a checkout)

For running Optio with **no source code at all**: the released Helm chart, the released images, and
Optio's work defined as code. `deploy/init.sh <folder>` copies it into your own deploy repo.

- `README.md` — the plan, phases 0–7: decide, bundle (outside), load, cluster prerequisites, ingress,
  install, bootstrap + configuration as code, operate; every chart gap and the configuration that
  covers it (no source change needed); Jira Data Center options.
- `CLAUDE.md` + skills `optio-deploy` (install, upgrade, roll back, symptom table) and
  `optio-config-as-code` (write, check, publish manifests) for the coding agent running it.
- `values/values.yaml` (annotated site values), `site/*.example` (env and secrets templates),
  `config/` (example manifests: a repo, GitLab issue → merge request, nightly dependency update, a Jira
  connection through the REST bridge, a Jira-triggered task left off until tested).
- Scripts (bash + coreutils + kubectl / helm / curl / skopeo): `bundle/fetch.sh` (outside) and
  `bundle/load.sh`, `images/build-agent-ca.sh` (upstream agent image + your CA),
  `scripts/make-k8s-objects.sh`, `deploy.sh` (pre-upgrade dump first), `apply-config.sh`,
  `bootstrap-db.sh`, `verify.sh`, `check-values.sh` (keys the chart doesn't know).

## Install (inside the air gap)

```bash
./install.sh --dry-run /path/to/optio          # see what would change
./install.sh /path/to/optio                    # core + airgap (default)
./install.sh --layer core /path/to/optio       # generic guides only
```

Then in the checkout: fill `docs/airgap/site-facts.md`, and per developer
`cp .claude/settings.local.example.json .claude/settings.local.json` (LiteLLM aliases, context window).
Re-running is safe. Team-owned files are only created when missing. `--prune` removes files a previous kit
version added and this one dropped. The install record is kept in `.git/`, never committed.

## Three ways to publish

| Mode                                   | How                                                                                                                                                | For                              |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| **Helper repo**                        | this repository: push it to your internal GitLab, or carry `git bundle create optio-agent-kit.bundle --all` through your approved transfer process | sharing the kit and its versions |
| **Merge request into your Optio fork** | `./make-pr.sh --layer all /path/to/optio` → branch `docs/agent-guides-airgap` + patch files                                                        | adopting it in the fork          |
| **Pull request to upstream Optio**     | `./make-pr.sh --layer core /path/to/optio` → branch `docs/agent-guides` + patch files; text in `PR_DESCRIPTION.md`                                 | contributing the generic part    |

`make-pr.sh` never pushes. It runs the repo's git hooks (prettier, typecheck, commitlint) like any commit;
`--no-verify` only when `node_modules` isn't installed.

## Keeping it true

Guides rot when code moves. In the Optio checkout:

1. `bash scripts/check-agent-guides.sh` after every upstream sync (skill `optio-refresh-guides` walks the fixes).
2. Edit the guides there, where you can test them against the code.
3. Bring the edits back here: `./harvest.sh /path/to/optio` (`--add-new` for new guide files), review
   `git diff`, run `tests/run-tests.sh`, bump `VERSION` and `OPTIO_BASE`, add a `CHANGELOG.md` entry, commit.

## Test

```bash
tests/run-tests.sh /path/to/optio      # needs an Optio checkout; works offline; leaves it untouched
```

It installs both layers into throwaway clones and checks: guides resolve, re-install is a no-op, team
files survive, the value map is deterministic and catches a stale chart, `impact.sh` answers, `make-pr.sh`
produces patches that `git am` cleanly, `harvest.sh` round-trips.

## Layout of this repo

| Path                                     | What                                                         |
| ---------------------------------------- | ------------------------------------------------------------ |
| `core/`, `airgap/`                       | the two layers, laid out exactly like the Optio repo         |
| `deploy/`                                | starter for a chart + images deploy repo (`deploy/init.sh`)  |
| `snippets/agents-md-section.md`          | the "Start here" section for the root `AGENTS.md`            |
| `install.sh`, `harvest.sh`, `make-pr.sh` | install, copy edits back, publish                            |
| `tests/run-tests.sh`                     | self-test against an Optio checkout                          |
| `VERSION`, `OPTIO_BASE`, `CHANGELOG.md`  | kit version, upstream commit it was checked against, history |
| `PR_DESCRIPTION.md`                      | text for the upstream pull request                           |
